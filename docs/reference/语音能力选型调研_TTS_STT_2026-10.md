# 语音能力选型调研：TTS / STT（2026-10）

> 调研范围：多语言（10+ 语种）、优先海外云 API、Markdown 交付。
> 数据口径：2026 年 10 月公开信息汇总。**价格与榜单每月都在变，签约前必须以官网/商务报价复核**，文中所有金额均为参考量级，不是报价承诺。

---

## 0. 结论先行

1. **不建议单供应商绑定。** 2026 年这个赛道的格局是「模型半年一换代、价格每季度往下走」，最优解是做一个薄薄的 provider 抽象层（统一 ASR/TTS 网关 + 评测集），业务代码只依赖自己的内部接口。
2. **实时交互场景，架构选择比模型选择更影响体验。** 级联（STT→LLM→TTS）与端到端语音模型（GPT-Realtime 2.x 一类）的延迟差 300–600ms，而这两条路在可控性、成本、可观测性上差异很大。建议「主链路级联 + 闲聊走实时模型」的混合方案。
3. **STT 首选梯队**：Deepgram Nova-3（流式延迟与价格最均衡）、AssemblyAI Universal-3.6 Pro（语义断句/对话能力）、ElevenLabs Scribe v2（90+ 语种、准确率强）。Google Chirp 3 与 Azure 强在生态与合规，单价明显更贵。
4. **TTS 首选梯队**：Cartesia Sonic 3.6（低延迟标杆）、ElevenLabs Eleven v4 / Flash v2.5（表现力与语种覆盖最强）、OpenAI gpt-4o-mini-tts（性价比 + 指令控制）。Google Chirp 3 HD、Azure 适合企业采购和已有云合同。
5. **Breeze TTS 2 技术上很强、生态很活跃，但权重是「研究用途」许可，商用前必须拿到授权或改用其托管 API。** 这是唯一一个「技术上想用、法务上要先过」的候选，详见第 5 节。
6. **成本结构**：以 10 万分钟/月 STT + 1000 万字符/月 TTS 估算，云 API 方案月成本落在 **$500–$4,000** 区间；若要自建一套支撑 50 路并发的 L4 集群，月成本约 **$2,600–$5,000**（含冗余与运维）。自建的经济性拐点大约在 30–50 万分钟/月，低于这个量自建是负优化。

## 1. 背景假设（请确认）

你只明确了「多语言 / 海外云 API / Markdown」，场景未选。本报告按以下假设推进：

| 假设项 | 取值 | 如果实际不同，会怎么变 |
|---|---|---|

| 语言 | 10+ 语种，假设英/西/葡/法/德/日 + 中/韩为主，需支持中英混说 | 若含小语种（泰、越、印尼、阿拉伯），ElevenLabs / Google 的语种覆盖优势放大 |

如果以上有偏差，第 8 节的评分权重需要重算。

## 2. 需求拆解：该拿哪些指标去卡

选型失败最常见的原因不是模型不行，而是评估口径错了。建议按下面这张表定义验收标准，PoC 阶段逐项打分。

**STT 侧**

| 指标 | 定义 | 建议门槛（实时交互） | 建议门槛（转写） |
|---|---|---|---|
| WER / CER | 词错率 / 字错率，按语种分别统计 | 主流语种 < 8%，带口音 < 15% | < 5%（可用后处理补偿） |
| 实体准确率 | 人名、地名、金额、邮箱、订单号、型号 | 关键实体 > 95% | > 98% |
| 首字延迟 | 音频开始到首个 partial 返回 | < 300ms | 不敏感 |
| 终版延迟 | 说话结束到 final 文本 | < 300ms（含端点检测） | 不敏感 |
| 端点检测（turn detection） | 能否区分「停顿」与「说完了」 | 必须支持，最好语义级 | 可选 |
| 时间戳 / 说话人分离 | 词级时间戳、diarization | 时间戳必须，分离可选 | 都必须 |
| 中英 code-switching | 一句话内混说 | 必须实测 | 必须实测 |
| 热词 / 上下文偏置 | 注入专有名词表 | 必须支持 | 必须支持 |

**TTS 侧**

| 指标 | 定义 | 建议门槛 |
|---|---|---|
| 首字节延迟（TTFB） | 请求到首帧音频 | 流式 < 200ms，理想 < 120ms |
| 实时率（RTF） | 生成耗时 / 音频时长 | < 0.3（留并发余量） |
| 自然度 | MOS 或成对比较（CMOS），盲测 | 与真人差距主观可接受，CMOS > -0.3 |
| 发音准确率 | 专名、数字、缩写、多音字 | 关键实体 > 98% |
| 语种一致性 | 同一音色跨语种是否「还是同一个人」 | 多语言产品必须验证 |
| 情感 / 风格控制 | 语速、停顿、情绪、耳语等标签 | 按产品需要 |
| 克隆质量与授权 | 少样本克隆相似度 + 商用授权范围 | 必须书面确认 |

> 榜单（Speech Arena / Artificial Analysis）只能当先验，不能当验收。所有厂商的中文、带口音英语、噪声场景，必须用你自己的 200–500 条金标集重测。

## 3. 技术路线：级联 vs 端到端

### 3.1 级联（STT → LLM → TTS）

主流做法，链路每一段都可替换、可观测、可灰度。延迟预算大约 700–1,200ms（p50），取决于 LLM 首 token 和 TTS 首字节。

优点：可插入 RAG、工具调用、审核、埋点；成本可精确归因；单段故障可降级。
缺点：三段延迟叠加；韵律与情绪在「文本→语音」这一跳丢失；打断（barge-in）需要自己做状态机。

### 3.2 端到端语音模型（Speech-to-Speech）

以 OpenAI GPT-Realtime 2.x 为代表：音频进、音频出，模型内部完成理解与生成，自带打断、轮次、语气延续。2026 年的版本在 p95 延迟上又降了约 25%，第三方测试里是最快的一档。

优点：延迟最低（可进 500ms 内）、语气自然、支持打断与副语言信息。
缺点：可控性差（难做严格话术、难插入业务规则）、按 token 计费在高并发下偏贵、可观测性弱、合规审查难（音频直连模型）。

### 3.3 推荐：混合

```
用户说话
  ├─ 意图 = 闲聊 / 情绪安抚  →  实时语音模型（低延迟、自然）
  └─ 意图 = 业务办理        →  级联链路（可控、可审计、可插工具）
```

路由用一个小分类器或规则即可。这样既拿到「像人」的体验，又保住业务链路的确定性。

### 5.3 专题：Breeze TTS 2 值不值得进候选

**它是什么**：BreezeBlue 于 2026 年 8 月发布的开放权重 TTS，官方仓库 `breezeblue-ai/breeze-tts`（PyTorch 推理），权重在 HuggingFace `BreezeBlue/Breeze-TTS-2`。架构是两阶段自回归：T5Gemma2 做文本编码，Qwen3 作 talker 主干 + 深度解码器，配自带的 Qwen3-TTS codec，输出 24kHz。同时提供 BreezeRT 低延迟推理框架、vLLM-Omni 支持、MLX / GGUF / ComfyUI 社区移植。

**优点**

- 开放权重里质量第一梯队：多家榜单给出约 1,215 Elo，曾登顶开放权重 TTS 榜（需注意与闭源第一名的差距，以及各家榜单口径不同）。
- 面向实时交互设计：流式合成、首包延迟可控，社区实测消费级显卡可跑，量化后显存需求很低（有 "4GB 显存可跑" 的说法，未独立验证）。
- 50 种语言，支持音色克隆、长文本、风格/语气指令（含耳语一类细粒度控制）。
- 生态已经起来了：ComfyUI 节点、MLX、GGUF、vLLM-Omni 都有，工程落地阻力小。

**风险（关键）**

1. **许可证是硬约束。** 官方模型卡写明：源码 Apache 2.0，但**模型权重、衍生模型与自托管输出为研究用途**。这意味着直接拿权重做商业产品输出，法务上站不住。要用只有两条路：向 BreezeBlue 取得商用授权，或改用其托管 API（breezeblue.ai 有商业服务）。
2. **50 种语言 ≠ 50 种语言都可用。** 中文、日文的实际自然度和多音字表现需要自测；社区中文资料多，但官方语种清单以模型卡为准。
3. **生产化配套要自己做。** 并发调度、显存管理、降级、监控都要自建；BreezeRT 是官方给的参考实现，不等于开箱即用的生产服务。
4. **版本迭代快。** 开放权重模型半年一代，自建意味着持续的模型维护成本。

**结论**：作为「技术备选 + 授权谈判筹码」很有价值，**不建议作为一期主方案**。合理动作是：立刻用 20 条样本跑一次盲测，把它和 ElevenLabs / Cartesia 放一起比；同时发一封商用授权询价。如果授权价格合理、且你的量足够大，它是最有希望把 TTS 单位成本打下来 60%+ 的选项。

### 6.4 自建的账要怎么算

自建的成本不是「GPU 小时 × 数量」，而是「峰值并发 × 冗余」。一个可用的估算模板：

- 语音并发 50 路、ASR RTF 0.05（turbo 级模型在 L4 上）→ 单卡可承载约 20 路，需要 3 卡，峰值冗余 2 倍 → 6 卡。
- L4/A10 租用约 $0.4–0.8/小时/卡 → 6 卡 × 730 小时 × $0.6 ≈ **$2,600/月**。
- 加上对象存储、带宽、监控、值班人力（按 0.5 人力计），总成本往往跑到 **$5,000+/月**。

**结论：只有在月音频量稳定超过 30–50 万分钟、或语种高度集中时，自建才比云 API 便宜。** 低于这个量，自建是负优化——省下的 API 费还不够付运维。如果确实要自建，先用一台机器跑「离线批量」任务（对延迟不敏感），把 GPU 利用率吃满，这是最稳的切入方式。

### 6.5 敏感性

成本最大的杠杆不是单价，而是**音频时长**。三个常见浪费点：静音段未做 VAD 切分被计费、TTS 重复合成相同话术未做缓存、长文本一次性整段合成导致失败重试全量重算。这三件事做好，账单通常能降 20–35%，比换供应商更划算。

## 7. 延迟预算

端到端目标 p50 < 1s。按级联链路的分解：

| 环节 | 目标 | 说明 |
|---|---|---|
| 上行网络 | 40–80ms | 就近接入区、Opus 编码、16–24kHz |
| VAD + 端点判定 | 150–300ms | 最难的一项；语义级判定比纯静音阈值体验好得多，但要多花 100–200ms |
| ASR 终版 | 100–250ms | 流式 partial 可先喂给 LLM，压缩感知延迟 |
| LLM 首 token | 250–500ms | 用小模型 + 短 prompt + 流式；这是最大的不确定项 |
| TTS 首字节 | 80–200ms | 流式合成，按句切分提前触发 |
| 下行网络 + 播放缓冲 | 60–150ms | 首包即播，别等整段 |

**优化顺序**（按性价比）：① LLM 首 token（换小模型/减 prompt/开缓存）→ ② 端点检测策略（用 partial 结果提前触发 LLM）→ ③ TTS 流式吐字 → ④ 网络就近。前两项做完通常能砍掉 300–400ms，剩下的才是换供应商能解决的。

如果目标要进 500ms，级联基本做不到，必须上端到端语音模型。

## 8. 选型建议

### 8.1 评分矩阵（按本报告假设场景）

权重：延迟 25%、准确率/自然度 20%、成本 20%、语种覆盖 15%、可控性与合规 10%、生态与运维 10%。

| 组合 | 延迟 | 质量 | 成本 | 语种 | 合规 | 运维 | 加权 |
|---|---|---|---|---|---|---|---|
| A. Deepgram Nova-3 + Cartesia Sonic 3.6 | 9 | 8 | 8 | 7 | 7 | 9 | **8.1** |
| B. Scribe v2 + Eleven v4 | 7 | 10 | 4 | 10 | 7 | 8 | **7.6** |
| C. AssemblyAI U-3.6 Pro + OpenAI mini-tts | 8 | 8 | 9 | 7 | 8 | 8 | **8.1** |
| D. GPT-Realtime 2.1（端到端） | 10 | 9 | 5 | 7 | 5 | 6 | **7.4** |
| E. 自建 Qwen3-ASR + Breeze/CosyVoice | 7 | 7 | 9（量大） | 6 | 10 | 4 | **7.2** |

> A 与 C 打平（均 8.1）。A 胜在流式延迟与生态成熟度，C 胜在成本、语义断句与 prompt 偏置能力。实际选择建议用 PoC 数据打破平局，而不是靠权重表。

### 8.2 推荐落地组合

**一期（0–3 个月，先跑通体验）**

- STT：Deepgram Nova-3，流式对话与批量转写共用一套账号，降低接入成本。
- TTS：Cartesia Sonic 3.6 做实时对话；品牌音/宣传物料用 ElevenLabs（按条计费，不影响主链路）。
- 架构：自建 `speech-gateway`，对外暴露统一接口（`transcribe` / `synthesize` / `stream`），内部按 provider 路由，带熔断与降级（主供应商超时自动切备）。

**二期（3–6 个月，做 A/B 与优化）**

- 接入 AssemblyAI 或 Scribe v2，用金标集做影子流量对比，按语种路由（例如英西用 Deepgram，日韩用 Scribe）。
- 闲聊/情绪场景接 GPT-Realtime 2.1-mini，业务场景继续走级联。
- 上线 TTS 缓存（固定话术）与 VAD 计费优化。

**三期（6 个月后，按量决策）**

- 月音频量 > 30 万分钟时，评估离线批量自建（Qwen3-ASR 或 Whisper-turbo）。
- 若 Breeze TTS 2 授权谈成，用它替换非实时配音链路，TTS 成本可降 60%+。
- 与主供应商谈年度承诺折扣（通常 15–30%）。

### 8.3 如果假设不成立

- **纯内容配音（有声书/短视频）**：把 TTS 提到第一优先级，选 ElevenLabs v4 或 Fish/Breeze（授权可行时），STT 可退化为可选能力；延迟权重降到 5%，音色一致性与长文本稳定性升到 30%。
- **纯会议转写**：STT 选 Scribe v2 或 Chirp 3（说话人分离 + 时间戳质量），TTS 几乎不需要；成本权重升到 30%，可大胆走批量自建。

## 9. 风险与合规

| 风险 | 影响 | 应对 |
|---|---|---|
| **声音克隆授权** | 法务与舆情风险最高的一项 | 克隆前取得本人书面授权；建立音色档案与撤回机制；对生成音频加不可听水印或元数据标记 |
| **Breeze TTS 2 权重许可** | 研究用途限制，商用直接输出可能违约 | 一期不用；授权谈判或改托管 API；法务书面留痕 |
| **数据驻留与跨境** | 欧盟/部分行业客户硬性要求 | 选供应商的 EU/US region 端点；PII 在入库前脱敏；保留可切私有化的架构 |
| **供应商锁定** | 涨价或停服 | provider 抽象层 + 双供应商热备；模型版本固定，不追最新 |
| **AI 生成内容披露** | 监管要求（EU AI Act 透明度、各地深伪规则） | 在产品侧做「AI 语音」标识；保留生成日志 |
| **价格波动** | 预算失准 | 按季度复核；合同锁价；成本监控按语种/场景拆分 |
| **榜单失真** | 选型误判 | 一切以自建金标集为准；榜单只用于筛候选 |

## 10. 落地路线（4–6 周 PoC）

**第 1 周｜定义与取样**
确定语言清单与优先级；每个语种采 50 条真实音频（含噪声、口音、中英混说、专有名词），共 300–500 条；同步准备 100 条 TTS 测试文本（含数字、缩写、多音字、长句）。

**第 2 周｜接入与跑分**
同时接入 3 家 STT（Deepgram / Scribe v2 / AssemblyAI）与 3 家 TTS（Cartesia / ElevenLabs / OpenAI）。写一个跑分脚本，输出 WER/CER、实体准确率、首字延迟、终版延迟、TTFB、CMOS。

**第 3 周｜真实链路压测**
在真实网络环境下测端到端延迟（p50/p95）；做 50 并发压测，观察限流与错误率；验证打断（barge-in）与端点检测在真实对话中的表现。

**第 4 周｜盲测与决策**
组织 10–15 人做 TTS 盲测（A/B 偏好），STT 用人工校对算真实 WER；汇总评分矩阵，出选型结论与合同要点。

**第 5–6 周｜灰度**
主备双活上线，5% 流量灰度，盯错误率与延迟；准备降级预案（供应商超时切备用、TTS 失败播预录提示音）。
